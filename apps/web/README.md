# @checkout/web

Фронтенд магазина: каталог, корзина, оформление заказа и тестовая оплата картой. React 19 + TypeScript, сборка на Vite, роутинг — react-router, работа с сервером — TanStack Query.

## Запуск

Из корня репозитория (там же лежит `package-lock.json` и настроены workspaces):

```sh
npm ci
npm run dev -w @checkout/api      # бэкенд на http://127.0.0.1:4000
npm run dev -w @checkout/web      # фронтенд на http://localhost:5173
```

Сборка и проверка типов:

```sh
npm run build -w @checkout/web    # tsc --noEmit + vite build, результат в apps/web/dist
npm run lint -w @checkout/web     # только проверка типов
```

Адрес API по умолчанию — `http://127.0.0.1:4000`, меняется через `VITE_API_URL` (см. `apps/web/vite.config.ts` / `.env`).

## Устройство работы с API

Весь обмен с сервером идёт через один слой в `src/api/`, компоненты и страницы напрямую `fetch` не вызывают.

- **`api/client.ts`** — единственное место, где собирается запрос: базовый адрес, `Authorization`, `Content-Type`, `Idempotency-Key`. Здесь же лежит единственная реализация разбора ответа: проверка `response.ok`, пропуск тела для `204`, `JSON.parse` с обработкой ошибки парсинга, извлечение `data` из конверта `{data, meta, links}`. Компонент никогда не видит сырой `Response` — только готовые типизированные данные или ошибку.
- **`api/errors.ts`** — один тип ошибки (`RequestError`) на все три источника проблем: сеть, HTTP-статус, разбор тела. Плюс словарь `friendlyMessage`, который переводит коды бизнес-ошибок сервера (`CART_VERSION_CONFLICT`, `INSUFFICIENT_STOCK`, `PAYMENT_IN_PROGRESS` и т.д.) в текст для пользователя, и `fieldErrorFor` — сопоставление серверных `fields[].path` с конкретным полем формы.
- **`api/endpoints.ts`** — тонкие типизированные функции по одной на ресурс API (`fetchCart`, `createOrder`, `simulatePayment`...). Здесь нет логики HTTP — только путь, метод и тип ответа; вся обработка уже сделана в `client.ts`.
- **`hooks/*`** — обвязка ресурсов в TanStack Query: `useQuery`/`useMutation` дают кеш, дедупликацию запросов, отмену устаревших запросов при размонтировании и (это отдельно важно для этой задачи) **поллинг** статуса оплаты и заказа через `refetchInterval`, который сам решает, продолжать опрос или остановиться, глядя на текущие данные. Своего цикла `setTimeout` для опроса в коде нет — это и есть общий переиспользуемый механизм ожидания/повтора, а не самописный для каждой страницы.
- Страницы (`pages/*`) получают из хуков уже готовые данные/ошибку и отвечают только за отображение: `QueryState` — один компонент для состояний «загрузка/ошибка/данные», используется во всех списках; `Field` — один компонент для подписи поля и текста ошибки под ним.

Если нужно поменять правило (например, добавить заголовок или изменить формат ошибки), меняется один файл — `client.ts` или `errors.ts`, — потребители не трогаются.

## Пример разбора данных (для критерия производительности)

`CatalogPage` и `CartPage` изначально были написаны так:

```ts
products.map((product) => {
  const cartItem = cart.items.find((item) => item.productId === product.id);
  ...
});
```

Это перерисовывается при каждом изменении корзины (добавление товара, смена количества), и для `N` товаров каталога и `M` позиций корзины даёт `O(N × M)` — на каждый товар отдельный линейный проход по корзине. Каталог сейчас маленький, но для витрины на сотни SKU это уже заметно, а главное — паттерн «линейный поиск внутри обхода» ровно то, что просят не делать.

Исправлено на:

```ts
const quantityByProductId = useMemo(() => {
  const map = new Map<string, number>();
  for (const item of cart?.items ?? []) map.set(item.productId, item.quantity);
  return map;
}, [cart]);
```

и дальше `quantityByProductId.get(product.id)` внутри `map()`. Индекс строится один раз на рендер, только когда действительно изменились данные корзины (`useMemo` с зависимостью на `cart`, а не на каждый рендер страницы), и каждый товар каталога ищет свою позицию за `O(1)`. Итог — `O(N + M)` вместо `O(N × M)`, один временный объект (`Map`) вместо неограниченного числа промежуточных результатов `find()`. То же самое сделано в `CartPage` для поиска остатка товара по `productId`. Точечных изменений (например, количество одной позиции) это тоже касается: `useMemo` не пересчитывает индекс, пока ссылка на данные корзины не поменялась, то есть несвязанные рендеры (например, тайпинг в поле формы на той же странице) индекс не трогают.

## Что проверено вручную

- Каталог → корзина (добавление, изменение количества, удаление, пустая корзина) → оформление (самовывоз и курьер, пересчёт стоимости при смене способа доставки) → оплата картой (успех, отказ с повторной попыткой, отмена) → страница успеха.
- Оплата наличными: заказ подтверждается сразу, без обращения к оплате.
- Двойной клик по «Оплатить»/«Оформить заказ» — кнопка блокируется на время запроса (`mutation.isPending`), повторный запрос переиспользует тот же `Idempotency-Key`.
- Перезагрузка страницы на `/orders/:id/payment` во время обработки платежа — состояние заказа и платежа восстанавливается по `orderId` из URL, опрос статуса продолжается.
- Устаревший ответ опроса не перезаписывает более новые данные и не продолжается после ухода со страницы — это обеспечивает TanStack Query (ключи запроса + отмена при размонтировании), отдельного кода для этого нет.
- Адаптивная раскладка проверена на 1280 и 390px (каталог, корзина, форма оформления, оплата) — горизонтальной прокрутки нет, элементы формы и кнопки доступны с клавиатуры.
- Конфликт версии корзины/устаревший расчёт при оформлении — данные обновляются, форма не сбрасывается.

## Известные недоработки

- Идентификатор попытки оплаты после перезагрузки восстанавливается через список `GET /api/orders/{id}/payments`, а не из `localStorage` — это проще и всегда синхронизировано с сервером, но означает лишний запрос при каждом заходе на страницу оплаты.
- Не реализована защита от одновременного изменения корзины в двух вкладках (второй вкладке нужно вручную обновить страницу, чтобы увидеть конфликт версии).
- Нет автоматических тестов на фронтенд-часть — сценарии проверены вручную и Playwright-скриптами золотого пути в ходе разработки.
